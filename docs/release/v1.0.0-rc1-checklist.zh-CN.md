## 真实项目验证目标

只读的业务仓库为：

```text
D:\02_工作\在研项目\NGUS2
```

用于验证的项目为：

```text
D:\02_工作\在研项目\NGUS2\NGUS2\NGUS2.csproj
```

观察到的目标事实：

- 面向 `.NET Framework 4.7.2` 的传统 WinForms 项目。
- AnyCPU 配置，具有现有发布输出
  `NGUS2\bin\Release\NGUSV3.2.exe`。
- AntdUI 被项目引用，并且存在于可执行文件旁。
- 该仓库包含本地工作树以及生成的分析/构建目录。它们位于此 fork 之外，
  RC 验证不得清理、回退或提交它们。

验证必须使用现有可执行文件进行 UIA/截图/交互检查。RuntimeBridge 实验
（如果需要）必须使用项目/输出的可丢弃副本；不得在业务仓库中进行任何包
引用或源文件修改。

## RC 验证证据

- 从临时目录启动了 `NGUS2\bin\Release` 的可丢弃副本；业务仓库保持未变更。
- `winforms_attach_to_process` 和 `winforms_get_process_status` 针对
  `NGUSV3.2.exe` 成功执行（响应正常、主窗口可见）。
- `winforms_get_element_tree` 返回了 48 个 UIA 节点，包括
  `gridPanel1`、`tabs1`、`pageHeader`、`documentPanel1` 以及标题栏
  控件。`winforms_get_property` 读取了真实的 `pageHeader.Name`。
- 进程截图生成了一个 1542 x 884 的 PNG。对未变更屏幕的两次捕获进行比较，
  返回 `changedPixelCount: 0`。
- 从有界的 UIA 树中发现了 AntdUI 的 `插入` 标签页，并通过其缓存的元素引用
  进行了操作。当提供程序不暴露桌面级后代查询时，嵌套控件应使用树返回的 ID。
- 运行时状态针对 NGUS2 正确地返回了结构化的不可用结果：
  目标是 `.NET Framework 4.7.2`，而 RuntimeBridge 当前面向
  `net48` 和 `net8.0-windows`。
- 在修复遗留输出/依赖问题后，使用 `providerProfile: AntdUI`、`theme:
  Light` 和 `dpi: 96` 渲染 `MainForm.Designer.cs` 成功，并生成了一个
  30,911 字节的 PNG，且不含 `Type not found` 占位符。

## 已知限制

- RuntimeBridge 是只读的。它有意不暴露属性设置器、任意方法调用、反射执行
  或业务对象。
- RuntimeBridge 当前支持 `net48` 和 `net8.0-windows`；一个 `net472`
  应用程序在没有兼容性实验或临时重新定向副本的情况下无法引用它。这是验证
  限制，而非修改 NGUS2 的许可。
- 模拟桌面输入的 UIA 操作需要可见桌面。无头模式应尽可能使用 `set_value` 等
  UIA 模式。
- 运行时和诊断快照是有界的。调用方必须遵守
  `maxDepth`、`maxNodes`、行/数量限制以及 `truncated` 标志。
- AntdUI 语义覆盖对提供程序/版本敏感，当内部缓存不可用时返回警告或按作用域
  的错误。
- 对于具有直接 `bin\Release` 输出的旧式项目，渲染器依赖发现现在优先选择最
  完整的程序集目录，并同时包含 DLL 和 EXE 输出。这不会使 `net472` 应用程序
  具备 bridge 能力。
- UIA 的 `find_element` 执行有界的桌面级查询。对于嵌套的自定义控件，请先
  调用 `get_element_tree`，并使用其缓存的 ID 执行操作。
- Windows 10 与 Windows 11 以及独立 .NET 10 执行尚未独立验证；
  `windows-latest` CI 是权威的 Windows 检查。
- 出于兼容性，`bridgeInstanceId` 为可选项。建议提供它，以便在目标进程重启
  后防止陈旧引用。
